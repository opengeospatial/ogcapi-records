== Catalogs and STAC Collections

This clause compares catalogs (record collections) with STAC Collections and explains how to create documents that are both. The normative provisions are in the <<clause_stac,Requirements Class "STAC">>.

[[sc_records-and-stac-collections_common-foundation]]
=== Common foundation

Catalogs and STAC Collections both extend the collection object of <<OGC17-069r4,OGC API - Features - Part 1: Core>>. They share the members `id`, `title`, `description`, `extent`, and `links` from OGC API - Features, and both add `keywords` and `license`. In both, `license` is an SPDX license identifier, an SPDX license expression, or `other`. The `type` member of a catalog has the value `Collection`, which is the same value that STAC Collections use. Both use `child` links for sub-catalogs and `item` links for records or STAC Items.

STAC defines two kinds of catalog objects: the STAC Catalog (`"type": "Catalog"`) and the STAC Collection (`"type": "Collection"`). OGC API - Records requires `"type": "Collection"` for all catalogs, so a catalog can only ever be a STAC Collection. A STAC Collection requires `description`, `license`, and `extent`, which are optional for catalogs. This applies to every catalog in a hierarchy, including catalogs that only group other catalogs and would be STAC Catalogs in a pure STAC implementation (see <<sc_records-and-stac-collections_structuring-catalogs>>).

[[sc_records-and-stac-collections_structuring-catalogs]]
=== Catalogs that only structure a hierarchy

Static STAC catalogs often use STAC Catalogs to structure a hierarchy, for example by year or by region, without describing any data themselves. Such a catalog cannot be a STAC Catalog in a document that is also a catalog of OGC API - Records, because <<OGC20-004r1,OGC API - Records - Part 1: Core>> fixes the `type` of catalogs to `Collection`. Leaving these nodes out of the Records hierarchy is not an option either, because clients of OGC API - Records follow `child` links only to catalogs.

These catalogs are therefore STAC Collections as well. STAC allows STAC Collections to contain other STAC Collections, and the STAC best practices recommend using the same structural element on each level of a hierarchy. Compared to a STAC Catalog, such a catalog needs a few more members:

* `extent`: the union of the extents of its sub-catalogs.
* `license`: the license that all of its sub-catalogs share. If they have different licenses, use `other` and add a link with the relation type `license` for each license. An SPDX license expression such as `CC-BY-4.0 AND CC0-1.0` is not suitable, because it states that all licenses apply to all of the data.
* `description`: a short description of the content, for example of the years or regions it contains.
* `itemType`: `catalog`, as it only has `child` links and no `item` links.

The `summaries` member is optional and can be left out. STAC clients present these catalogs as STAC Collections instead of as STAC Catalogs, for example with their extent.

[[sc_records-and-stac-collections_differences]]
=== Differences

<<collection-crosswalk>> lists the members that differ between catalogs and STAC Collections. <<sc_records-and-stac-collections_creating>> describes what these differences mean in practice, and its steps can be used as a checklist to check whether a catalog is also a valid STAC Collection.

[#collection-crosswalk,reftext='{table-caption} {counter:table-num}']
.Differences between catalogs of OGC API - Records and STAC Collections
[cols="20,40,40",options="header"]
|===
|Member |Catalog of OGC API - Records |STAC Collection
|`id` |Required. |Required. Unique across all STAC Collections in the root STAC Catalog.
|`stac_version` |Not defined. |Required.
|`stac_extensions` |Defined by this Standard. |Optional.
|`conformsTo` |Optional. Applies to the catalog and all of its records. |Not defined. Allowed as an additional member.
|`description` |Optional. Can be an empty string. |Required. The STAC JSON Schemas do not allow an empty string.
|`license` |Optional. The license under which the catalog is made available. |Required. The license of the data.
|`extent` |Optional. As defined by OGC API - Features: the first bounding box and the first interval describe the overall extent, further ones describe more precise extents. Optional `crs` and `trs` members. |Required. Same meaning. Exactly two bounding boxes are not allowed. Always WGS 84 and the Gregorian calendar, timestamps in UTC.
|`itemType` |Optional. `record`, `catalog`, or both. A catalog in a Records API requires `record`. |Not defined. Allowed as an additional member.
|`crs` |Optional. The coordinate reference systems used for the spatiotemporal values of the catalog and its records, for example their geometries. |Not defined. The Projection extension describes the coordinate reference system of the data instead, for example with `proj:code` in `summaries` or assets.
|`created`, `updated` |Optional. |Optional, as STAC common metadata.
|`contacts`, `themes`, `language`, `languages` |Optional. |Available through STAC extensions, see <<overlapping-extensions>>.
|`resourceLanguages`, `rights` |Optional. |Not defined.
|`providers` |Not defined. |Optional. Organizations that produced, processed, licensed, or host the data.
|`summaries` |Not defined. Allowed by this Standard, see <<per_stac-extensions_summaries,/per/stac-extensions/summaries>>. |Strongly recommended. Summaries of the members of the STAC Items.
|`assets`, `item_assets` |Not defined. Allowed by this Standard, see <<per_stac-extensions_assets,/per/stac-extensions/assets>>. |Optional.
|`records`, `recordsArrayName` |Optional. Records encoded in the catalog. |Not defined. STAC clients only find STAC Items through `item` links or an API.
|`schemes` |Optional. |Not defined.
|Required links |`self`, and `alternate` for each other representation. |None. `self` and `root` are strongly recommended.
|Links to sub-catalogs |`child`, and also `related` for sets of catalogs and `next` for series. |`child` only. `related` links are not part of the hierarchy.
|===

Both ecosystems require the `links` member, reference an API endpoint for records or STAC Items with an `items` link, and recommend `parent` and `root` links in sub-catalogs.

Temporal intervals in the `extent` of both catalogs and STAC Collections use `null` for an open start or end. This is different from the `time` member of a record, which uses `..`.

The `license` member of a catalog and of a STAC Collection describe different things, see <<sc_stac_license>>.

[[sc_records-and-stac-collections_creating]]
=== Creating a catalog that is also a STAC Collection

. Add `stac_version` with the value `1.1.0` or a later version 1.x.x, as required by <<req_stac_version,/req/stac/version>>.
. Add `description`, `license`, and `extent`. `description` cannot be an empty string. For a catalog that only groups other catalogs, see <<sc_records-and-stac-collections_structuring-catalogs>>.
. In `extent`, do not use exactly two bounding boxes, use UTC timestamps, and leave out `crs` and `trs` or use their defaults.
. If `license` is not a single SPDX license identifier, add links with the relation type `license`, as recommended by <<rec_stac_license,/rec/stac/license>>.
. Provide `providers` in addition to `contacts`. STAC clients typically show `providers`, and clients of OGC API - Records show `contacts`. Alternatively, list the Contacts extension in `stac_extensions`.
. Add `root` and `parent` links, and set the media types of hierarchical links as required by <<req_stac_link-media-types,/req/stac/link-media-types>>. Use `child` links for sub-catalogs, because STAC clients only crawl `child` links as part of the hierarchy.
. Do not rely on records encoded in the `records` member. STAC clients do not read them.
. Add `summaries` for the most important members in the `properties` of the records, for example `type` or `proj:code`. The keys in `summaries` are the member names without the prefix `properties.`.
. Keep `conformsTo` and add the conformance classes of this Standard.

A catalog in JSON is served as `application/ogc-catalog+json` by default. STAC clients expect `application/json`. <<OGC20-004r1,OGC API - Records - Part 1: Core>> also allows `application/json` for catalogs, with the profile `http://www.opengis.net/def/profile/OGC/0/ogc-catalog` to identify the content. Serving catalogs as `application/json` with a `profile` link works for both ecosystems. In an API that declares the "JSON" conformance class, `application/json` is only available through content negotiation, because `application/ogc-catalog+json` stays the default media type for catalogs (see <<sc_apis_interoperability>>). Crawlable catalogs only need to declare the "Crawlable Catalog" conformance class and can serve their catalogs as `application/json`. Records are served as `application/geo+json` in both ecosystems and carry a `profile` link to `http://www.opengis.net/def/profile/OGC/0/ogc-record`, which STAC clients ignore.

[[sc_records-and-stac-collections_from-collection]]
=== Creating a catalog from a STAC Collection

A STAC Collection is already very close to a catalog. To make it useful for clients of OGC API - Records:

. Start from a STAC Collection. A STAC Catalog cannot be a catalog of OGC API - Records, because its `type` is `Catalog`. It can be turned into a STAC Collection, see <<sc_records-and-stac-collections_structuring-catalogs>>.
. Add `itemType` with the value `record` if the collection references STAC Items, `catalog` if it only references other collections, or both.
. Add a `conformsTo` member with `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/record-collection` and the conformance classes of this Standard. In a static catalog, also add `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog`.
. Make sure that the collection has a `self` link, and add a link with the relation type `alternate` for each other representation, for example HTML.
. Check the meaning of `license`. In a STAC Collection, it is the license of the data, while OGC API - Records applies it to the catalog itself. If the two differ, describe the license of the catalog in the `rights` member.
. Add `contacts` in addition to `providers`. Clients of OGC API - Records show `contacts`, and STAC clients typically show `providers`.
. Consider adding other members of a catalog that STAC does not define, for example `themes` or `language`.

[[sc_records-and-stac-collections_example]]
=== Example

The following catalog is also a valid STAC Collection. It is the catalog of the record shown in the <<clause_stac,Requirements Class "STAC">>. The data and the catalog are available under the same license, so its `license` means the same in both ecosystems. `providers` lists the producer for STAC clients. The `profile` link identifies the document as a catalog for clients of OGC API - Records.

.A catalog that is also a STAC Collection
====

----
{
  "type": "Collection",
  "stac_version": "1.1.0",
  "id": "dutch-metadata",
  "itemType": "record",
  "conformsTo": [
    "http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/record-collection",
    "http://www.opengis.net/spec/ogcapi-records-5/1.0/conf/stac-extensions",
    "http://www.opengis.net/spec/ogcapi-records-5/1.0/conf/stac"
  ],
  "stac_extensions": [
    "https://stac-extensions.github.io/contacts/v1.0.1/schema.json"
  ],
  "title": "Dutch metadata",
  "description": "Metadata of Dutch geospatial datasets, harvested from the Nationaal Georegister.",
  "keywords": ["Netherlands", "datasets"],
  "license": "CC-BY-4.0",
  "extent": {
    "spatial": {
      "bbox": [[3.37087, 50.7539, 7.21097, 53.4658]]
    },

          "2010-01-01T00:00:00Z",

        ]
      ]
    }

      "name": "Rijksinstituut voor Volksgezondheid en Milieu (RIVM)",

          "value": "info@rivm.nl"
        }

    }
  ],

    {
      "rel": "self",
