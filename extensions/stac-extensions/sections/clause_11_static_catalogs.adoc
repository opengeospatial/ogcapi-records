== Crawlable catalogs and static STAC catalogs

This clause compares crawlable catalogs of OGC API - Records with static STAC catalogs and explains how to publish one set of static files for both ecosystems.

=== Terminology

Both ecosystems support catalogs that consist only of static files, without an API. OGC API - Records calls them _crawlable catalogs_ ("Crawlable Catalog" requirements class). STAC calls them _static catalogs_.

OGC API - Records also defines a _local resources catalog_ ("Local Resources Catalog" requirements class). Despite the similar name, it is not a static catalog. A local resources catalog is an API endpoint such as `/collections` that can be searched like a catalog, see <<clause_apis,Records APIs and STAC APIs>>.

=== Common foundation

A crawlable catalog consists of catalogs that reference their records with `item` links and their sub-catalogs with `child` links. A static STAC catalog consists of STAC Catalogs and STAC Collections that reference their STAC Items with `item` links and their sub-catalogs with `child` links. Crawlers of both ecosystems can therefore traverse the same files, as long as each file is valid in both.

=== Where interoperability breaks

The following situations make a static catalog work in one ecosystem but not in the other:

* A catalog or record without `stac_version`. STAC clients do not recognize the document as a STAC entity and stop crawling at this point. A hierarchy is only fully usable by STAC clients if every catalog and record in it is a STAC entity.
* Links to sub-catalogs with the media type `application/ogc-catalog+json`. STAC clients do not follow them, see <<req_stac_link-media-types,/req/stac/link-media-types>>.
* Records that are encoded in the `records` member, or catalogs that are only connected through `related` or `next` links. STAC clients do not crawl them as part of the hierarchy.
* A catalog without a `self` link. This is allowed in STAC, and recommended for catalogs that are meant to be copied, but not in OGC API - Records. STAC tools may remove `self` links from sub-catalogs when saving a catalog, unless it is saved as a catalog with absolute links.
* Files that the web server or object storage serves with a generic media type such as `application/octet-stream`. Both ecosystems rely on the media type.
* A `self` link that points to another location than the one the file is served from, for example after copying the catalog to a mirror. Clients then resolve relative links against different base URIs, see <<clause_links,Links and URL resolution>>.
* A `conformsTo` member in a catalog. OGC API - Records requires it in crawlable catalogs, but in STAC, `conformsTo` usually indicates the landing page of a STAC API. STAC clients may therefore present the root of a static catalog as an API, or try to use API endpoints that do not exist.

=== Detecting static catalogs and APIs in clients

Clients that support both ecosystems cannot rely on the presence of a `conformsTo` member to tell a static catalog from an API:

* In a crawlable catalog, `conformsTo` is expected in each catalog and can also be present in records. It contains `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog`.
* A STAC API declares its conformance classes in the `conformsTo` member of its landing page and, for "STAC API - Features" and "STAC API - Collections", also at the `/conformance` endpoint (see <<clause_apis,Records APIs and STAC APIs>>).
* A Records API declares its conformance classes at the `/conformance` endpoint.

Clients therefore check for specific conformance classes instead, for example `https://api.stacspec.org/v1.0.0/core` for a STAC API or `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/searchable-catalog` for a Records API, and only use the API functionality that the declared conformance classes describe.

=== Publishing a static catalog for both ecosystems

. Make every catalog a STAC Collection and every record a STAC Item, as described in <<clause_records-and-stac-collections,Catalogs and STAC Collections>> and <<clause_records-and-stac-items,Records and STAC Items>>, and follow the <<clause_stac,Requirements Class "STAC">>.
. Publish the catalog at a fixed location. Give every catalog and every record a `self` link with an absolute URI. Other links can be relative. If the catalog moves, update the `self` links.
. Add `root` and `parent` links to all catalogs and records.
. Use `child` links for sub-catalogs and `item` links for records.
. Declare conformance in the `conformsTo` member of each catalog: `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog` and the conformance classes of this Standard.
. Configure the web server or object storage to serve records as `application/geo+json` and catalogs as `application/json`, and add a `profile` link with `http://www.opengis.net/def/profile/OGC/0/ogc-catalog` to each catalog.
. Follow the STAC file naming conventions. They are consistent with the `{id}.json` recommendation of OGC API - Records for record files.

The following folder structure is an example. Each record is stored in its own folder, next to the data it describes, as recommended by both ecosystems.

----
atlas/
├── collection.json
└── energy/
    ├── collection.json
    └── b7d2fd24-8cd8-4965-a997-69eb1a987b5a/
        ├── b7d2fd24-8cd8-4965-a997-69eb1a987b5a.json
        └── data.tif
----

All catalogs in this example are STAC Collections, so their files are named `collection.json`. OGC API - Records does not prescribe file names for catalogs.

=== Example

The following sub-catalog `energy/collection.json` is part of a crawlable catalog and a static STAC catalog. It has an absolute `self` link, as required by OGC API - Records, and relative links to the other files.

.A sub-catalog of a crawlable catalog that is also a STAC Collection
====

----
{
  "type": "Collection",
  "stac_version": "1.1.0",
  "id": "energy",
  "itemType": "record",
  "conformsTo": [
    "http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/record-collection",
    "http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog",
    "http://www.opengis.net/spec/ogcapi-records-5/1.0/conf/stac"
  ],
  "title": "Energy",
  "description": "Datasets about energy from the Atlas Leefomgeving.",
  "license": "CC-BY-4.0",
  "extent": {
    "spatial": {
      "bbox": [[3.37087, 50.7539, 7.21097, 53.4658]]
    },
    "temporal": {
      "interval": [
        ["2019-04-16T00:00:00Z", "2019-04-16T23:59:59Z"]
      ]
    }
  },
  "links": [
    {
      "rel": "self",
      "type": "application/json",
      "href": "https://example.org/atlas/energy/collection.json"
    },
    {
      "rel": "root",
      "type": "application/json",
      "title": "Atlas Leefomgeving",
      "href": "../collection.json"
    },
    {
      "rel": "parent",
      "type": "application/json",
      "title": "Atlas Leefomgeving",
      "href": "../collection.json"
    },
    {
      "rel": "profile",
      "href": "http://www.opengis.net/def/profile/OGC/0/ogc-catalog"
    },
    {
      "rel": "alternate",
      "type": "text/html",
      "title": "This catalog as HTML",
      "href": "./index.html"
    },
    {
      "rel": "item",
      "type": "application/geo+json",
      "title": "Zonpotentie velden",

    {
      "rel": "license",
