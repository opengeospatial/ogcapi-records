== Crawlable catalogs and static STAC catalogs

This clause compares crawlable catalogs of OGC API - Records with static STAC catalogs and explains how to publish one set of static files for both ecosystems.

=== Terminology

Both ecosystems support catalogs that consist only of static files, without an API. OGC API - Records calls them _crawlable catalogs_ ("Crawlable Catalog" requirements class). STAC calls them _static catalogs_.

OGC API - Records also defines a _local resources catalog_ ("Local Resources Catalog" requirements class). Despite the similar name, it is not a static catalog. A local resources catalog is an API endpoint such as `/collections` that can be searched like a catalog, see <<clause_apis,Records APIs and STAC APIs>>.

=== Common foundation

A crawlable catalog consists of catalogs that reference their records with `item` links and their sub-catalogs with `child` links. A static STAC catalog consists of STAC Catalogs and STAC Collections that reference their STAC Items with `item` links and their sub-catalogs with `child` links. Crawlers of both ecosystems can therefore traverse the same files, as long as each file is valid in both.

Both ecosystems allow relative and absolute links, reference sub-catalogs with `child` links and records or STAC Items with `item` links, and recommend `root` and `parent` links in sub-catalogs.

=== Where interoperability breaks

The following situations make a static catalog work in one ecosystem but not in the other:

* *Missing `stac_version`:* A catalog or record without `stac_version`. STAC clients do not recognize the document as a STAC entity and stop crawling at this point. A hierarchy is only fully usable by STAC clients if every catalog and record in it is a STAC entity.
* *Media type of links to sub-catalogs:* Links to sub-catalogs with the media type `application/ogc-catalog+json`. STAC clients do not follow them, see <<req_stac_link-media-types,/req/stac/link-media-types>>.
* *Records and catalogs outside the hierarchy:* Records that are encoded in the `records` member, or catalogs that are only connected through `related` or `next` links. STAC clients do not crawl them as part of the hierarchy.
* *Missing `self` link:* A catalog without a `self` link. This is allowed in STAC, and recommended for catalogs that are meant to be copied, but not in OGC API - Records. STAC tools may remove `self` links from sub-catalogs when saving a catalog, unless it is saved as a catalog with absolute links.
* *Moved catalogs:* A `self` link that points to another location than the one the file is served from, for example after copying the catalog to a mirror. Clients then resolve relative links against different base URIs, see <<clause_links,Links and URL resolution>>.
* *`conformsTo` in catalogs:* A `conformsTo` member in a catalog. OGC API - Records requires it in crawlable catalogs, but in STAC, `conformsTo` usually indicates the landing page of a STAC API. STAC clients may therefore present the root of a static catalog as an API, or try to use API endpoints that do not exist.

=== Detecting static catalogs and APIs in clients

Clients that support both ecosystems cannot rely on the presence of a `conformsTo` member to tell a static catalog from an API:

* *Crawlable catalogs:* In a crawlable catalog, `conformsTo` is expected in each catalog and can also be present in records. It contains `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog`.
* *STAC APIs:* A STAC API declares its conformance classes in the `conformsTo` member of its landing page and, for "STAC API - Features" and "STAC API - Collections", also at the `/conformance` endpoint (see <<clause_apis,Records APIs and STAC APIs>>).
* *Records APIs:* A Records API declares its conformance classes at the `/conformance` endpoint.

It is therefore recommended that clients check for specific conformance classes instead, for example `https://api.stacspec.org/v1.0.0/core` for a STAC API or `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/searchable-catalog` for a Records API, and only use the API functionality that the declared conformance classes describe.

=== Publishing a static catalog for both ecosystems

A static catalog can serve both ecosystems in two ways. In the first, every file is valid in both ecosystems. In the second, a hierarchy combines files that are only valid in one of the ecosystems, and each ecosystem only follows the links to the files it can read.

==== Files that are valid in both ecosystems

. Make every catalog a STAC Collection and every record a STAC Item, as described in <<clause_records-and-stac-collections,Catalogs and STAC Collections>> and <<clause_records-and-stac-items,Records and STAC Items>>, and follow the <<clause_stac,Requirements Class "STAC">>.
. Publish the catalog at a fixed location. Give every catalog and every record a `self` link with an absolute URI. Other links can be relative. If the catalog moves, update the `self` links.
. Add `root` and `parent` links to all catalogs and records.
. Use `child` links for sub-catalogs and `item` links for records.
. Declare conformance in the `conformsTo` member of each catalog: `http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog` and the conformance classes of this Standard.
. Configure the web server or object storage to serve records as `application/geo+json` and catalogs as `application/json`, and add a `profile` link with `http://www.opengis.net/def/profile/OGC/0/ogc-catalog` to each catalog.
. Optionally, add the `profile` member with the value `["http://www.opengis.net/def/profile/OGC/0/ogc-catalog"]` to the links to catalogs. Clients of OGC API - Records then know that the target is a catalog before they retrieve it, while STAC clients ignore the member.
. Follow the STAC file naming conventions: `collection.json` for catalogs, as they are STAC Collections, and `{id}.json` for records, each in its own folder next to the data it describes. They are consistent with the `{id}.json` recommendation of OGC API - Records for record files. OGC API - Records does not prescribe file names for catalogs.

==== Mixed hierarchies

A hierarchy can also combine catalogs and records of OGC API - Records that are not STAC entities with STAC Catalogs, STAC Collections, and STAC Items that are not records. The media types of the links tell the clients which links to follow:

* *Catalogs that are valid in both ecosystems:* The root and every catalog that links to both kinds of sub-catalogs need to be valid in both ecosystems, as described above. Otherwise, the clients of one ecosystem cannot enter the hierarchy or reach the sub-catalogs.
* *Links to catalogs of OGC API - Records:* Links to catalogs that are not STAC Collections use the media type `application/ogc-catalog+json`. STAC clients skip them, and clients of OGC API - Records know that the target is a catalog.
* *Links to STAC Catalogs and STAC Collections:* Links to STAC entities that are not catalogs of OGC API - Records use the media type `application/json` without the `ogc-catalog` profile. STAC clients follow them. Clients of OGC API - Records can tell from the missing profile that the target is not a catalog.
* *Records and STAC Items:* Both use the media type `application/geo+json`, so the media type cannot tell them apart. Records that are not STAC Items are therefore only linked from catalogs of OGC API - Records, and STAC Items that are not records only from STAC Catalogs and STAC Collections.
* *Conformance:* Each catalog declares only the conformance classes that it and its records conform to. A catalog that is valid in both ecosystems but links to catalogs of OGC API - Records that are not STAC Collections still declares the "STAC" conformance class, because the declaration covers the catalog and its records, not its sub-catalogs (see <<req_stac_conformance,/req/stac/conformance>>).

=== Example

The following sub-catalog `energy/collection.json` is part of a crawlable catalog and a static STAC catalog. It has an absolute `self` link, as required by OGC API - Records, and relative links to the other files.

====

{
  "type": "Collection",
  "stac_version": "1.1.0",

  "itemType": "record",

    "http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/record-collection",
    "http://www.opengis.net/spec/ogcapi-records-1/1.0/conf/crawlable-catalog",
    "http://www.opengis.net/spec/ogcapi-records-5/1.0/conf/stac"

  "description": "Datasets about energy from the Atlas Leefomgeving.",
  "license": "CC-BY-4.0",
  "extent": {
    "spatial": {
      "bbox": [[3.37087, 50.7539, 7.21097, 53.4658]]
    },
    "temporal": {
      "interval": [
        ["2019-04-16T00:00:00Z", "2019-04-16T23:59:59Z"]
      ]
    }
  },
  "links": [
    {
      "rel": "self",
      "type": "application/json",
      "href": "https://example.org/atlas/energy/collection.json"
